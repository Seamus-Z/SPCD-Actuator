## 第一部分：评估方法论

### 1.1 为什么需要指标

「代码写得好不好」如果只能靠感觉，就无法管理：不能设门禁、不能看趋势、不能对齐团队认知。
本节先定义**可测量、可自动化、有业界参照**的指标体系，后续所有结论都挂在这套指标上。

指标设计遵循三条原则：

1. **可自动测量** —— 能写进 CI 的才是指标，需要人工判断的是评审意见
2. **有参照基线** —— 单独一个数字没有意义，必须有「好/坏」的分界
3. **与后果挂钩** —— 每个指标要能说清「超标了会发生什么」

### 1.2 十大评估维度

| # | 维度 | 回答的问题 | 权重 |
|---|---|---|---|
| D1 | 模块化与依赖治理 | 改一处会不会牵连一片？ | 12% |
| D2 | 可扩展性 | 加个新功能要动多少地方？ | 15% |
| D3 | 可读性与认知负荷 | 新人多久能看懂并安全修改？ | 12% |
| D4 | 可测试性 | 改完怎么知道没坏？ | 15% |
| D5 | 接口契约管理 | 上下位机/模块间会不会悄悄对不上？ | 10% |
| D6 | 功能安全与鲁棒性 | 出异常时会不会烧东西？ | 15% |
| D7 | 构建可复现性 | 换台机器/换个人能不能编出来？ | 8% |
| D8 | 可观测性 | 出问题能不能定位？ | 5% |
| D9 | 变更成本与维护性 | 长期维护会不会越来越慢？ | 5% |
| D10 | 发布与配置管理 | 版本/参数能不能追溯？ | 3% |

> 权重按「嵌入式电机驱动产品」的场景设定：安全和可测试性权重最高，
> 因为失效后果是物理损坏；可观测性权重较低，因为本项目已有较强的遥测能力。

### 1.3 指标定义与基线

#### D1 模块化与依赖治理

| 指标 | 测量方法 | 优秀 | 可接受 | 危险 |
|---|---|---|---|---|
| 循环依赖数 | 构建图分析 | 0 | 0 | ≥1 |
| 核心算法层外部依赖 | `math/` 的非本层 include 数 | 0 | ≤2 | ≥5 |
| 单模块平均文件行数 | LOC / 文件数 | <250 | 250~400 | >400 |
| 依赖规则是否机器强制 | BUILD/lint 是否阻断违规 | 是 | 部分 | 否（仅文档约定）|

#### D2 可扩展性

| 指标 | 测量方法 | 优秀 | 可接受 | 危险 |
|---|---|---|---|---|
| **变更扇出**（新增同类功能需改的文件数）| git diff --stat | ≤3 | 4~6 | ≥7 |
| 新增功能的重复代码率 | 同类函数行级相似度 | <30% | 30~60% | >60% |
| 是否存在扩展点抽象 | 有无 interface / 策略模式 | 有 | 部分 | 无（if-else 平铺）|
| 协议扩展是否破坏兼容 | 旧客户端能否继续工作 | 兼容 | 需版本协商 | 直接失效 |

> **变更扇出**是本报告最重视的可扩展性指标。它直接等于「加功能的人力成本」和
> 「漏改一处导致 bug 的概率」。业界经验：扇出 ≥7 时，遗漏率显著上升。

#### D3 可读性与认知负荷

| 指标 | 测量方法 | 优秀 | 可接受 | 危险 |

| 最大函数长度 | 行数 | <50 | 50~120 | >120 |
| 最大文件长度 | 行数 | <500 | 500~1000 | >1000 |
| 单文件分支总数 | if/else/switch/for/while 计数 | <60 | 60~150 | >150 |
| 类的公开+私有方法数 | 声明计数 | <20 | 20~35 | >35 |

> 8~15% 通常是在解释「为什么这么做」（有价值）。

## 第三部分：逐维度详评

### D1 模块化与依赖治理 — 4.5/5

#### 实测数据

| 指标 | 实测 | 基线 | 判定 |
|---|---|---|---|
| 循环依赖 | 0 | 0 | 优秀 |
| `math/` 外部 include | **0**（17 个头文件全部只引用 `math/` 内部）| ≤2 | 优秀 |
| 依赖规则机器强制 | 是（BUILD `deps` + `visibility`）| 是 | 优秀 |
| 单模块平均文件行数 | `app` **410** / `math` 214 / `HAL` 186 | <250 | app 超标 |

#### 分析

`math/` 层做到了真正的零依赖，这是全项目最有价值的架构资产。它意味着：
FOC、PID、轨迹生成、六种辨识算法都可以在 PC 上编译、推理、调试，
不需要板子、不需要示波器。

更关键的是这条规则**被写进了构建系统**而不只是文档：

```python
# fw/math/BUILD
# Pure motor-control algorithms. These targets must not depend on HAL, device,
# telemetry, NVS, or application code.
cc_library(
    name = "servo_mode",
    deps = [":base", ":foc"],   # ← 白名单，加不进去 HAL
)
```

想违规就编译不过。这比 code review 里靠人记得提醒可靠得多。

#### 扣分点

`fw/app` 平均 410 行/文件，其中 `application.cc` 独占 1715 行。
编排层缺少内部再分层（模式管理 / 遥测组包 / 配置应用 混在一起）。

#### 建议与收益

| 建议 | 收益 |
|---|---|
| 把 `application.cc` 按职责拆成 `application.cc`（生命周期）、`control_modes.cc`（模式分派）、`telemetry_builder.cc`（遥测组包）、`runtime_config.cc`（配置应用）| 单文件回到 400~500 行区间；改遥测不会碰到控制逻辑，降低误伤；git 冲突面减小 |
| 在 CI 加一条依赖检查（`bazel query 'deps(//fw/math:all)'` 断言不含 HAL）| 把现有的隐性保证变成显式回归，防止未来有人为了图快加依赖 |

### D2 可扩展性 — 2.0/5

#### 实测数据

| 指标 | 实测 | 基线 | 判定 |
|---|---|---|---|
| **变更扇出**（新增 MIT 模式）| **11 文件 / +334 行** | ≤3 | **危险** |
| 同类函数重复率 | `StartCurrent` vs `StartMit` **82%** | <30% | **危险** |
| 扩展点抽象 | 无（8 个布尔量 if-else 平铺）| 有 | **危险** |
| 协议向后兼容 | 优秀（8/20/48 三种 payload 并存）| 兼容 | 优秀 |

#### 分析：加一个模式到底要做什么

以刚完成的 MIT 模式为例，实测 `git diff --stat`：

```
fw/app/inc/application.h            |   4 +      ← 声明 StartMit + 成员
fw/app/inc/board_config.h           |  12 +      ← MitModeOptions 工厂
fw/app/src/application.cc           | 181 ++++    ← 构造/StartMit/ISR分支/遥测/StopOutput/ApplyConfig
fw/app/src/binary_commands.cc       |  15 +      ← payload 解析
fw/math/BUILD                       |   1 +      ← 新头文件
fw/telemetry/inc/telemetry/xt_can.h |  14 ++     ← kModeMit + kServoCtrlMit + 注释
tools/host/gui/static/app.js        |  17 +      ← 按钮回调
tools/host/gui/static/index.html    |  16 +      ← 输入框
tools/host/gui/web_server.py        |  26 +      ← 流式打包 + API
tools/host/test_xt_proto.py         |  20 +      ← 用例
tools/host/xt_proto.py              |  37 +      ← pack_mit
11 files changed, 334 insertions(+)
```

其中**固件侧 `application.cc` 的 181 行分散在 6 个位置**：
构造函数、`StartMit`、`StopOutput`、`ControlIsrStep` 的标志位、`ControlIsrStep` 的分支、
`BuildTelemetry`、`BuildCtrlReply`、`ApplyRuntimeConfig`。

**漏改任何一处的后果**：

| 漏改位置 | 症状 | 排查难度 |
|---|---|---|
| `StopOutput` | 切模式后旧模式仍在算，力矩叠加 | 高（间歇性）|
| `BuildCtrlReply` | 遥测显示错误模式/位置 | 中 |
| `ApplyRuntimeConfig` | 改 Config 对新模式不生效 | 高（静默）|
| ISR 标志位 | 模式永不激活或与其他模式打架 | 低（明显）|

这就是扇出 11 的真实代价 —— 不是多打字，是**多了 6 个静默出错的机会**。

#### 重复代码证据

```
StartServo   vs StartCurrent : 64% 行级相似
StartServo   vs StartMit     : 63% 行级相似
StartCurrent vs StartMit     : 82% 行级相似   ← 几乎是复制粘贴
```

三个函数共享的模板：

```cpp
检查 state_ / init_ok            // 完全相同
检查 encoder_.valid()            // 完全相同
如果已在本模式 → SetCommand 后返回  // 结构相同
停止其他模式                      // 完全相同
dq_modulator_->Stop()            // 完全相同
DisableControlIsr()              // 完全相同
SampleBlocking() + ResetPll()    // 完全相同
本模式 Start(command)             // ← 唯一真正不同的一行
foc_->Start(cmd)                 // 几乎相同
Step 一次 + 检查失败              // 完全相同
SetDuty / PowerOn / mode_ =      // 结构相同
StartControlIsr()                // 完全相同
```

真正的差异只有 3~5 行，却复制了 60~80 行。

#### 建议与收益

**建议 E-1a：引入 `ControlMode` 接口**

```cpp
// fw/app/inc/control_mode.h
class IControlMode {
 public:
  virtual ~IControlMode() = default;
  // ISR 上下文：返回 Iq 参考，false 表示要求停机
  virtual bool Step(float dt_s, const Feedback& fb, float* iq_out) = 0;
  virtual void Stop() = 0;
  virtual bool active() const = 0;
  virtual uint8_t mode_id() const = 0;
  // 可选：往 CtrlReply 里填自己的字段
  virtual void FillReply(telemetry::xt_can::CtrlReply* r) const {}
};
```

`ControlIsrStep` 退化成：

```cpp
if (active_mode_ == nullptr) { DisableIsrAndReturn(); return; }
float iq;
if (!active_mode_->Step(dt_s, feedback, &iq)) { StopOutput(); return; }
foc_->SetRefs(0.0f, iq + encoder_.CoggingCurrentCompensation());
// ... 统一的 FOC + PWM 输出
```

**建议 E-1b：抽出 `EnterMode()` 模板**

把三个 `Start*` 的公共部分提成一个函数，各模式只提供「本模式 Start」这一个回调。

| 收益 | 量化 |
|---|---|
| 变更扇出 11 → **4~5** | 新增模式只需：算法文件 + 注册一行 + 协议枚举 + GUI |
| 消除 82% 重复 | `Start*` 三函数 208 行 → 约 80 行 |
| 消除 6 个静默漏改点 | 编译器强制实现所有接口方法 |
| `ControlIsrStep` 425 行 → 约 80 行 | 认知负荷断崖式下降 |
| 每个模式可独立单测 | 与 D4 改进叠加 |

> **注意**：ISR 内虚函数调用有开销（约 3~5 个周期的间接跳转）。
> 在 170 MHz / 66.7 µs 预算下完全可接受；若在意，可用 CRTP 或函数指针表替代虚函数。

**建议 E-2：MIT 参数改用专属字段**

现状把 `id_mA` 当 Kp、`iq_mA` 当 Kd 用。48 B 的 `ServoRequest` 里，
MIT 模式下 `stop_position` / `velocity_limit` / `accel_limit` / 三个 scale 共 **18 字节完全闲置**。

| 建议 | 收益 |
|---|---|
| 下次协议版本升级时，用闲置的 `velocity_limit_mrad_s` / `accel_limit_mrad_s2` 承载 Kp/Kd，或定义 union | 抓包分析时字段名与语义一致；未来 MIT 若需要 Id 前馈仍有位置；减少新人误读 |

### D3 可读性与认知负荷 — 2.5/5

#### 实测数据

| 指标 | 实测 | 基线 | 判定 |
|---|---|---|---|
| 最大函数长度 | **`ControlIsrStep` 425 行** | <50 | **严重超标 8.5×** |
| 最大文件长度 | **`application.cc` 1715 行** | <500 | **超标 3.4×** |
| 单文件分支数 | `application.cc` **210** | <60 | **超标 3.5×** |
| 类方法数 | `Application` **51 个私有方法** | <20 | **超标 2.5×** |
| 注释密度 | `telemetry` 8.7% / `math` 4.4% / **`middleware` 1.4%** | 8~15% | 部分偏低 |
| 魔数散落 | `* 1000.0f` / `* 0.001f` 共 **64 处** | ≤3 | **危险** |
| TODO/FIXME | **0** | <1/kLOC | 见下方说明 |

#### 分析

**优点先说**：`math/` 层的可读性相当好。函数短、命名一致（`Step` / `Start` / `Stop` / `result()`）、
关键决策都有「为什么」注释。例如：

```cpp
// Transport delay ~= 1.5 PWM periods (sample->apply) plus the MA600 group
// delay. Keep this tied to Ma600Options().filter_us so the two cannot drift
// apart again (64us lead with 1024us filter → 60 rad/s runaway; 1124us lead
// with 1024us filter → ~80 rad/s ceiling).
```

这条注释记录了一次真实事故的两个数据点，是**高价值注释**的范本 ——
它解释了「为什么代码必须长这样」，而不是「代码在做什么」。

**问题集中在编排层**。`ControlIsrStep` 425 行意味着：

- 屏幕一次显示约 50 行，需要**滚动 8.5 屏**才能看完一个函数
- 人的工作记忆容量约 4~7 个 chunk，这个函数有 8 个模式布尔量 + 十几个中间变量
- 修改时无法在脑内完整模拟所有路径，只能局部推理 → 局部推理正是漏改的来源

**魔数问题**：`* 1000.0f`（单位转换 rad ↔ mrad、A ↔ mA、Nm ↔ mNm）出现 **37 次**，
`* 0.001f` 出现约 27 次。这类代码：

```cpp
command.kp_nm_per_rad = static_cast<float>(req.id_mA) * 0.001f;
r.theta_mech_mrad = static_cast<int32_t>(encoder_.pll().position_rad() * 1000.0f);
```

看起来无害，但它把「单位」这个重要信息藏在了裸数字里。写错方向（乘变除）
不会报错，只会让数值差 10⁶ 倍。

**TODO 为 0 的解读**：这不是优点。项目明显存在技术债（本报告列了 10 条），
但代码里一条 TODO 都没有，说明**债务没有在代码现场被标记**。
后来者读到有问题的代码时，无法区分「这是刻意为之」还是「这是欠着的」。

#### 建议与收益

| 编号 | 建议 | 收益 |
|---|---|---|
| R-1 | 引入强类型单位（`struct Milliamp { int32_t v; }` 或至少 `constexpr float kMilli = 0.001f;` + 命名转换函数 `MradToRad()` / `RadToMrad()`）| 编译期阻止方向写反；64 处魔数变成自解释调用；新人不必反复确认单位 |
| R-2 | 拆分 `ControlIsrStep`（配合 D2 的接口化，自然降到 ~80 行）| 可在一屏内读完；修改时能完整推理；review 效率提升 |
| R-3 | 拆分 `application.cc` 为 4 个文件（见 D1 建议）| 单文件 <500 行；职责边界显式化 |
| R-4 | 给 `middleware/` 补注释（当前 1.4%），重点说明 `EncoderService` 的补偿链顺序与 `CalibrationManager` 的 dirty/persisted 状态机 | 这两个类是「数据从传感器到算法」的必经之路，理解成本最高但注释最少 |

#### S-1：无看门狗

**现状**：控制 ISR 跑在 15 kHz，主循环无限循环。没有任何硬件看门狗。

**失效场景**：

| 触发原因 | 后果 |
|---|---|
| SPI 读 MA600 挂死（时钟异常/线缆松动）| ISR 卡在等待，**PWM 保持最后一次占空比** |
| 栈溢出（8 KB 栈，标定累加器较大）| 跳到 `AppHardFault` 闪灯，但 **PWM 输出未关** |
| Flash 操作异常阻塞 | 同上 |
| 主循环卡死 | 超时保护失效，ISR 继续按最后命令驱动 |

关键点：**PWM 外设是硬件自主运行的**。CPU 卡死不会让 PWM 停，
它会一直按最后写入的比较值输出。如果卡死瞬间是 80% 占空比、Iq=5 A，
电机就会**持续以 5 A 堵转**直到有人拔电。

**建议**：

```cpp
// main.cpp 初始化后
IWDG->KR = 0x5555; IWDG->PR = 3; IWDG->RLR = 1000;  // ~500 ms
IWDG->KR = 0xCCCC;

// RunOnce() 末尾（注意：喂狗必须放主循环，不能放 ISR）
IWDG->KR = 0xAAAA;
```

**为什么喂狗必须在主循环而不是 ISR**：如果放在 ISR 里，主循环卡死时 ISR 还在跑、
还在喂狗，看门狗永远不触发 —— 那就白装了。放主循环则 ISR 和主循环任一卡死都会复位。

补充建议：在 `AppHardFault` 里**第一件事是关 PWM 输出**（写 `TIM5->BDTR &= ~TIM_BDTR_MOE`
或直接拉 DRV 的 `enable` 脚），再闪灯。

| 收益 | 说明 |
|---|---|
| 消除「软件死亡但电机通电」这一类失效 | 从「可能烧毁」降级为「复位后停机」|
| 成本极低 | 约 10 行代码，无运行期开销 |

#### S-2：无软件过流 / 过温保护

**现状**：只有 DRV8353S 的硬件 VDS 阈值（700 mV）。那是**短路保护**，
响应的是「桥臂击穿」这种毫秒级灾难，不响应「持续 4 A 堵转把绕组烤了」这种秒级~分钟级热失效。

`max_phase_current_A = 4.9 A` 只是 FOC 参考值的钳位，不是实测电流的保护。
如果电流环失稳导致实际电流超过参考值，没有任何机制会介入。

**建议**：

1. **I²t 积分限流**：累积 `∫(I² − I_rated²)dt`，超阈值降额或停机。
   这是绕组热模型的一阶近似，能覆盖「短时大电流可以，长时中等电流不行」的真实物理。
2. **峰值硬保护**：ISR 内检测 `|I| > I_max × 1.2` 连续 N 个周期 → 立即 `StopOutput`。
3. **温度采样**：至少采 MOSFET 或 PCB 温度，超阈值线性降额 `max_iq`。
4. **母线电压 ADC**：现在 `bus_V` 是常量 48 V。如果实际母线跌到 36 V，
   调制器会算出错误的占空比；如果泵升到 60 V，会过调制。

| 收益 | 说明 |
|---|---|
| 覆盖热失效这一整类故障 | 硬件 VDS 完全不管这块 |
| 降额而非直接停机 | 产品化后用户体验更好（性能下降 vs 突然罢工）|
| 母线采样让调制精度提升 | 顺带改善低压时的电流环表现 |

#### S-3：Flash 写入期间失控窗口

**现状**：

```cpp
// calibration_manager.h PersistPending()
if (phase_pwm_ != nullptr) {
  phase_pwm_->DisableControlIsr();   // 关 ISR
}
const bool saved = nvs::MotorConfigStore::Save(data);  // 数十 ms 页擦除
```

关了 ISR，但**没有关栅极驱动输出**。STM32G4 页擦除 20~40 ms，
这段时间 PWM 硬件仍在按最后占空比输出，而控制环已经停止。

标定刚结束时转子往往还在惯性旋转 —— 此时换相角度不再更新，
相当于给一个转动的电机施加固定电角度的电压矢量，会产生制动力矩或异常电流。

**建议**：

```cpp
// 写 Flash 前
gate_driver_->PowerOff();          // 先断输出
phase_pwm_->SetDuty(kMin,kMin,kMin);
// 可选：等待 |ω| < 阈值
phase_pwm_->DisableControlIsr();
Save(...);
```

进阶方案：双页 ping-pong + 分片写入，把单次阻塞从数十 ms 降到单次 double-word 写入
（几十 µs），ISR 完全不用关。

| 收益 | 说明 |
|---|---|
| 消除无控输出窗口 | 从「数十 ms 失控」到「0」|
| 标定流程更安全 | 标定是最容易出现「刚停但还在转」的场景 |

## 第六部分：总结

### 一句话判断

> 这是一个**算法深度和架构直觉明显超出工程化成熟度**的项目。

### 三个最值得肯定的决策

1. **`math/` 零依赖并由构建系统强制** —— 这是整个项目最有价值的资产，
   它让 3640 行控制算法保持了可推理、可移植、可测试的形态
2. **`static_assert` 锁 ABI** —— 把线格式从「约定」变成「编译期契约」，
   19 处断言挡住了整类通信错误
3. **无堆 + 静态池 + 确定性启动** —— 对 15 kHz 硬实时是完全正确的取舍

### 三个最需要立刻改的地方

1. **加看门狗**（S-1）—— 10 行代码，消除「软件死亡但电机通电」这一整类物理风险
2. **修构建可复现性**（B-1）—— 半天工作，让项目从「单机可用」变成「任何人可用」
3. **给 `math/` 写测试**（T-1）—— 1~2 天起步，兑现架构已经准备好的最大红利

### 最核心的一句建议

> **你已经把 `math/` 设计成了可测试的形态，却一个测试都没写 —— 这是全项目最大的浪费。**
>
> 补上测试不需要改任何架构，只需要写测试文件。而一旦有了测试，
> E-1 那个 425 行的巨函数重构才敢做，之后每加一个功能都会省 60% 的力气。

从投入产出看，建议的顺序是：**安全兜底 → 构建可复现 → 补测试 → 再重构**。
前三步共约两周，之后这个项目就具备了「多人协作」和「产品化」的基础条件。
